# Comptes Démo Commerciaux — Spec Produit

> **Objectif :** Permettre à nos commerciaux de créer en quelques minutes un compte démo hyper-réaliste pour un prospect, avec une flotte simulée adaptée à son activité, pour convertir en direct ou à distance.

---

## 1. Vision & Positionnement

Le compte démo est l'**arme de conversion #1** des commerciaux Mycelium. Il doit :

- Montrer la valeur de la plateforme avec les **propres données du prospect** (secteur, taille, pays)
- Simuler une flotte **vivante et crédible** — véhicules qui se déplacent, alertes qui tombent, KPIs qui bougent
- Créer un sentiment d'urgence naturel avec une **date d'expiration visible**
- Déclencher la conversion via une **modale de clôture infranchissable** à la fin du test

Le commercial ne devrait pas avoir besoin de 45 min de préparation. Cible : **compte opérationnel en < 3 minutes**.

## 3. Architecture Technique

### 3.1 Table `demoOrganizations`
Extension de la table `organizations` avec des champs démo :

```typescript
organizations: {
  // ... champs existants ...
  isDemo: v.optional(v.boolean()),
  demoConfig: v.optional(v.object({
    templateId: v.string(),           // 'btp' | 'services' | 'distribution' | ...
    createdBy: v.string(),            // userId du commercial
    commercialName: v.string(),       // Nom du commercial (pour modale de fin)
    commercialPhone: v.string(),      // Téléphone cliquable dans la modale
    commercialCalendlyUrl: v.optional(v.string()),
    prospectName: v.string(),         // Nom du contact prospect
    prospectEmail: v.optional(v.string()),
    notes: v.optional(v.string()),    // Notes internes commercial
    expiresAt: v.number(),            // Timestamp d'expiration
    extendedCount: v.number(),        // Nombre de fois prolongé (max 3)
    isExpired: v.boolean(),
    convertedAt: v.optional(v.number()),
    conversionSource: v.optional(v.union(
      v.literal('call'),
      v.literal('calendly'),
      v.literal('self_serve')
    ))
  }))
}
```

### 3.2 Table `demoVehiclePositions`
Stocke les dernières positions simulées (updated par cron) :

```typescript
demoVehiclePositions: defineTable({
  vehicleId: v.id('vehicles'),
  organizationId: v.id('organizations'),
  lat: v.number(),
  lng: v.number(),
  speed: v.number(),           // km/h, 0 si garé
  heading: v.number(),         // 0–360°
  status: v.union(
    v.literal('moving'),
    v.literal('parked'),
    v.literal('charging'),
    v.literal('idle')
  ),
  fuelOrSocPercent: v.number(), // 0–100%
  odometerKm: v.number(),
  updatedAt: v.number()
})
  .index('by_vehicle', ['vehicleId'])
  .index('by_org', ['organizationId'])
```

### 3.3 Simulation Engine (`convex/demo/simulation.ts`)

#### Algorithme de mouvement réaliste
```
Chaque véhicule suit un circuit géographique centré sur l'adresse du prospect (+/- 50km rayon).

1. SÉQUENCE JOURNALIÈRE (basée sur le template) :
   - 06:30–08:00 : départ dépôt → premier site (accélération progressive)
   - 08:00–12:00 : activité principale (déplacements, arrêts)
   - 12:00–13:30 : pause déjeuner (garé)
   - 13:30–17:30 : activité PM
   - 17:30–19:00 : retour dépôt / domicile
   - 19:00–06:30 : garé (SoC remonte si électrique)

2. VARIABILITÉ (évite l'effet "trop parfait") :
   - ±15% sur les horaires
   - 20% des véhicules BTP actifs le samedi matin
   - 5% des VTC actifs la nuit (missions aéroport)
   - Vitesse variable selon contexte (ville 30–50, route 90, autoroute 110–130)

3. CARBURANT / BATTERIE :
   - Décroissance proportionnelle à la distance (L/100 ou Wh/km selon énergie)
   - Recharge simulée : batterie < 20% → statut 'charging' pendant 1–4h
   - Diesel : passage "station" aléatoire si < 15% → remonte à 95%

4. ÉVÉNEMENTS AUTOMATIQUES (générés avec probabilités) :
   - Alerte maintenance (1 véhicule/semaine basée sur km)
   - Contravention reçue (1 événement/mois aléatoire)
   - Permis proche expiration (1 conducteur simulé/mois)
   - Alerte consommation anormale (1 par template/semaine)
```

#### Cron de simulation (`convex/crons.ts`)
```
// Toutes les 5 minutes : mise à jour positions démo
simulateDemoFleets → internal.demo.simulation.updateAllDemoPositions

// Quotidien 6h UTC : génération événements démo (maintenance, alertes, IK)
generateDemoEvents → internal.demo.simulation.generateDailyDemoEvents
```

### 3.4 Données de Conducteurs Simulés
Chaque template génère des conducteurs fictifs avec :
- Noms réalistes selon la locale (FR/UK/SE/NO/DK)
- Scores éco-conduite variant de 62 à 94
- Historique de réservations plausible (30–60 jours de passé simulé)
- Permis B (+ C/D si template BTP ou transport)

## 4. UX Flows

### 4.1 Création d'un compte démo (commercial)

**Accès :** `/concierge/demos/new` — visible super_admin + rôle `sales` (nouveau rôle à créer)

**Wizard 4 étapes :**

**① Infos prospect**
- Nom de l'entreprise (pré-remplit le nom de l'org démo)
- Secteur d'activité → sélecteur 7 templates avec aperçu visuel
- Pays (GB / FR / SE / NO / DK / DE / NL) → adapte locale + devise + BiK/CSRD
- Taille estimée de flotte (slider : 15–150 véhicules)
- Nom du contact prospect + email + téléphone

**② Paramètres démo**
- Date d'expiration (par défaut J+14, max J+30)
- Infos commercial (nom, téléphone direct, lien Calendly optionnel)
- Notes internes (non visibles du prospect)
- Option : notifier le prospect par email à la création

**③ Prévisualisation**
- Aperçu de la flotte générée (3–5 exemples de véhicules)
- Aperçu du dashboard KPIs qui sera visible
- Carte géographique centrée sur… (champ ville/code postal pour centrer la simulation)

**④ Création**
- Bouton "Créer le compte démo"
- Génération asynchrone (5–10s) : création org + véhicules + conducteurs + historique 30j + positions initiales
- Résultat : lien magique `/demo/[token]` copiable d'un clic + bouton "Ouvrir la démo"

---

### 4.2 Expérience prospect (accès au compte démo)

Le prospect accède via le lien magique `/demo/[token]` :
- Connexion auto sans mot de passe (session démo) **ou** création compte basique
- Interface identique à un vrai compte Mycelium (pas de watermark "démo" visible)
- Bandeau discret en haut : `"Démo Mycelium · Expire le [date] · Des questions ? Appelez [nom commercial]"`
- Toutes les features actives selon le plan Professional (niveau max pour la démo)
- L'agent Concierge IA répond avec des données de la flotte simulée

## 6. Génération du Lien Magique

```
/demo/[token]
```

- Token : 48 hex chars (24 bytes crypto-random)
- Table `demoAccessTokens` : `{ token, organizationId, createdAt, lastUsedAt, usedCount }`
- Pas d'expiration propre au token (suit l'expiration de l'org démo)
- En option : lien personnel par prospect `demo-prospect@[org].mycelium.io` redirect vers `/demo/[token]`
- Le lien peut être envoyé par email depuis l'interface (template Resend branded)

## 9. Sécurité & Isolation

- **Multi-tenant strict :** une org démo est une vraie org Convex, isolée par `organizationId`
- **Aucune donnée réelle :** les véhicules simulés ont des plaques fictives (AA-000-AA pattern distinct)
- **Pas d'accès inter-orgs :** un token démo ne donne accès qu'à son org démo
- **Pas d'API calls sortants :** la simulation est 100% interne Convex (pas d'appels GPS externes)
- **Cleanup automatique :** cron hebdomadaire supprime les orgs démo expirées depuis > 60 jours

## 12. Notes d'Implémentation

**Plaques fictives :** Format `DM-[3 chiffres]-[2 lettres]` (DM = Demo Mycelium), clairement distinguables en base mais pas visibles dans l'UI (l'UI affiche le modèle/nom du véhicule en priorité).

**Données géographiques :** La simulation utilise des routes réelles via des waypoints pré-calculés par région (Île-de-France, Greater London, Göteborg, etc.) stockés en JSON static — pas d'API cartographique en temps réel.

**Scale :** Une org démo de 80 véhicules génère ~400 updates/5min en cron. Avec 50 démos actives simultanées = 20 000 updates/5min → acceptable avec Convex (bien dans les quotas action).

**Rôle `sales` :** Nouveau `staffRole` à ajouter en plus de `super_admin` et `concierge`. Accès : création/gestion démos uniquement. Pas d'accès aux orgs clients réelles.
